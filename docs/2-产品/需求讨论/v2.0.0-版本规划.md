# Starcat 2.0.0 版本规划

> 状态：版本范围已确认，尚未开始代码实施。
> 确认日期：2026-10-12。
> 本轮授权：整理规划文档、细化 Linux.do 接入方案；不修改业务代码。
> 代码核对基线：主仓库 `dev`，`c2525c46`。源码观察不代表运行时验收。

## 1. 版本目标与范围

2.0.0 围绕三项主要交付展开：增加社区项目发现能力、降低设置理解和配置成本、统一业务图标。交互与性能先收集问题和证据，再按影响安排整改。

| 优先级 | 方向 | 本版本交付边界 |
|---|---|---|
| P0 | Linux.do 项目发现 | 采集、项目识别、独立分类、跨分类来源标识、原帖追溯形成完整链路 |
| P1 | 设置页面重构 | 调整配置归属，解释用途与依赖，每个分类增加说明卡片 |
| P1 | 图标体系整理 | 保留语义准确的 SF Symbols，用统一图标库补齐业务图标，缺失部分定制 |
| P2 | 交互与 UI 问题收集 | 形成可复现、可分级的问题清单和简要优化方向 |
| P2 | 性能问题收集 | 明确测量场景、指标和候选瓶颈，形成后续优化清单 |

前三项是主要交付内容。后两项本轮以问题清单和调查结果为交付，不承诺全部整改。新增功能直接引入的回归仍由对应功能修复，不因优化专项优先级低而忽略。

本文件是 **2.0.0 的版本范围基线**；[早期 v2 功能规划](v2-功能规划.md)继续作为历史需求池。旧池中的待办不会自动进入本版本，已取消项目不会因本次规划重新启用。取消范围遵循[2026-10-07 决议](../../4-工程进度/2026-10-07-任务取消与范围同步.md)。

## 2. Linux.do 项目发现

### 2.1 用户可见行为

- 暂定入口为“探索 → 发现 → Linux.do”，保持为发现内的来源分类。
- 收录“开源推广”标签公开主帖中实际推广的公开 GitHub 仓库；首版处理主帖及主帖编辑。
- 一篇帖子允许关联多个项目，一个项目允许关联多篇帖子，仓库按 GitHub repository ID 去重。
- 分类列表提供原有仓库浏览能力，并显示来源与关联帖子数；默认按推广时间排序，普通回复顶帖不改变推广时间。
- 仓库详情增加“Linux.do 讨论”区域，支持查看帖子标题、时间和原帖链接。
- Stars、知识库、其他发现来源等入口中，同一仓库均可呈现 Linux.do 来源标识。
- 收录只增加公共目录与来源事实；Star、标签、笔记、知识库状态继续由用户控制。

### 2.2 采集与运营边界

首选站方允许的结构化接入。2026-10-12 实测：未登录的标签 JSON 请求返回 403；[标签 RSS](https://linux.do/tag/2234-tag/2234.rss)返回 200，包含 30 条帖子，抽查条目的正文摘要内有 GitHub 链接。因此优先验证 RSS 增量方案；分页 API / 站方导出作为完整性补充。RSS 可读不等于持续采集与再利用已获许可，也不能保证完整历史、全部编辑和删除均可发现。

优先复用 `starcat-discovery-api` 的仓库元数据、调度、缓存和管理能力，为 Linux.do 增加独立目录与来源关系。当前 Discovery、Awesome 的目录边界继续保留。

主帖中出现的所有 GitHub 链接都只是候选；依赖、竞品、示例、徽章和引用内容不能直接当作推广项目。明确的结果可自动收录，歧义结果进入人工复核。公开可访问与采用开源许可证是两项独立事实。

首版不包含评论区全量采集、非 GitHub 仓库适配、论坛内评论或登录操作，也不承诺完整历史回填。具体接入路径、识别规则、数据契约与验收用例见 [Linux.do 项目发现与来源标识接入方案](../../3-设计/详细设计/70-Linux.do项目发现与来源标识接入方案.md)。

| ID | 交付项 | 验收重点 |

## 3. 设置页面重构

### 3.1 当前问题与已有能力

[SettingsView](../../../Starcat/Features/Settings/SettingsView.swift)目前定义 20 个分类入口。用户反馈设置复杂，特别是普通搜索和 RAG 的向量相关配置难以区分。

代码已通过 [resolveEmbeddingSelection](../../../Starcat/Features/AI/AIConfiguration.swift)统一解析向量模型；[语义搜索](../../../Starcat/Features/AI/SemanticSearchService.swift)和 [RAG 索引](../../../Starcat/Core/RAG/KnowledgeRAGIndexBuilder.swift)共用该选择。重构重点是配置归属和用途表达；不能把现有共享模型误写为两套独立模型。

| 配置层次 | 用途 | 目标呈现 |
|---|---|---|
| 向量模型 | 把文本转换成相似度匹配数据 | 统一配置，显示使用该模型的功能 |
| 仓库搜索索引 | 按含义找到仓库 | 展示仓库覆盖、更新状态和重建操作 |
| 知识库内容索引 | 为问答检索 README、笔记、摘要等证据 | 独立展示内容覆盖和处理状态 |
| 检索后端与参数 | 选择存储、召回、重排与预算 | 常用项有推荐值，专业参数按需展开 |

两类索引分别维护；换模型时说明影响范围与重建需求。没有向量模型时仍保留知识库关键词检索能力，遵循[开发前问题清单 §5.16](../../1-立项/开发前问题清单.md)。

### 3.2 信息架构草案

首轮按以下十组梳理所有现有配置。名称、页内层级和逐项归属在设置专项中进一步确认，不以压缩分类数替代可用性验证。

| 建议分类 | 主要归属 |
|---|---|
| 通用与外观 | 语言、主题、字号、Dock 与应用行为、渠道更新入口 |
| 通知与快捷键 | 通知策略、分类订阅、应用快捷键、输入行为 |
| 账户与隐私 | GitHub 权限、Pro 许可、数据贡献与隐私说明 |
| AI 与模型 | 供应商、凭据、本地模型、共享向量模型、任务模型分配 |
| 翻译 | 系统翻译、第三方翻译服务、AI 翻译的选择与状态 |
| 自动整理 | 标签整理、GitHub Lists 分组等后台能力 |
| 搜索与知识库 | 两类索引、知识库问答的检索与提示词、联网搜索；模型引用统一入口 |
| 扩展与连接 | 浏览器插件、MCP、CLI / 本地工具、自建服务地址 |
| 数据与存储 | 数据目录、缓存用量、已有维护与数据操作 |
| 诊断与实验 | 诊断导出、日志入口、Labs 与高级诊断能力 |

复杂能力通过页内分组或子页进入，设置搜索应能直接定位具体控件。模型、API Key 等基础配置只保留一个编辑归属，消费方展示有效配置和跳转入口。

### 3.3 分类说明卡片

每个分类顶部使用统一结构：分类图标、标题、一句话用途、影响范围，以及有意义的状态或相关入口。

示例文案：

> 搜索与知识库
>
> 配置仓库搜索和知识库问答使用的检索能力。
>
> 两项功能共用向量模型，仓库索引与知识库内容索引分别维护。

卡片遵循 [DESIGN.md](../../../DESIGN.md)的原生工具风格，使用紧凑间距、系统语义色和清晰表面层次。说明卡片是分类解释组件，其余控件继续沿用原生表单。具体样板确认后再同步相关 UI 规范。

### 3.4 交付与验收

- 全量设置项建立“旧位置 → 新位置 → 生效范围”映射，避免遗漏或重复编辑入口。
- 常用项优先展示；高级参数有默认值、用途解释和恢复路径。
- 延续自动保存，并区分保存成功、连接验证成功、配置生效时机。
- 保留既有配置、Keychain 凭据、深链跳转与渠道差异，不要求用户重新设置。
- 分类说明卡片、长文本、大字号、明暗主题和错误反馈完成样板验收。

## 4. 图标体系整理

选型方向为 **SF Symbols + Lucide + 少量定制业务图标**。Lucide 是已选的补充库方向，具体替换映射和定制图形仍需样板确认。

| 图标类型 | 处理原则 |
|---|---|
| 系统操作 | 关闭、复制、刷新、删除、展开等继续复用现有共享组件和合适的 SF Symbols |
| 业务含义 | 核对 Awesome、自动整理、索引、工作台等入口，语义不准确时替换 |
| 品牌来源 | GitHub、Linux.do 等优先采用允许使用的官方标识，统一容器与尺寸 |
| 库中缺失的业务图形 | 列出缺口，按统一网格、线宽、圆角和视觉重量成批制作 |

首批样板候选：Awesome 的 `eyeglasses` 对比 Lucide [library-big](https://lucide.dev/icons/library-big)；AI 自动整理的循环箭头对比 [workflow](https://lucide.dev/icons/workflow)。样板必须检查是否与知识库、刷新等现有含义混淆，不能仅因图形更好看而替换。

Lucide [SVG 规范](https://lucide.dev/contribute/icons/code-conventions)使用 24×24 网格、默认 2px 描边与圆角端点。最终在 Starcat 的 13/15/18pt 场景做光学校准。缺失图标先生成同风格设计稿，经确认后整理为可维护的矢量资产，并验证明暗主题、字号缩放、选中与禁用状态。

交付物包括图标语义对照表、样板、缺失图标资产、集中语义映射与使用规范。同一功能在侧栏、设置、工具栏和空状态保持同一含义。引入资源必须按照 [Lucide 许可证](https://lucide.dev/license)及项目[开源致谢规范](../../5-规范/开源致谢同步-规范.md)登记；部分 Feather 衍生图标另有 MIT 声明。

## 5. 交互与 UI 问题收集

下表是待调查清单，不代表所有问题均已复现。本轮未执行 GUI 操作。每项调查补充复现路径、证据、影响用户、建议和验收方法，再决定是否进入开发。

| ID | 场景 | 需要检查的问题 | 简要优化方向 |
|---|---|---|---|
| UI-01 | 主侧栏 | Stars、知识库、标签、Lists、智能集合的区别是否清楚 | 核对命名、分组和说明 |
| UI-02 | 搜索与筛选 | 范围、有效筛选、空结果原因是否可见 | 明确当前上下文和恢复入口 |
| UI-03 | 仓库列表 | 来源、状态、评分等信息是否过密 | 确定信息顺序，收敛次要标记 |
| UI-04 | 仓库详情 | README、洞察、Wiki、AI 的入口与主路径是否明确 | 按阅读任务组织辅助动作 |
| UI-05 | 批量操作 | 当前页、已加载结果、全部结果的选择范围是否清楚 | 显示范围、数量及执行结果 |
| UI-06 | AI / RAG | 缺模型、缺索引、无结果、请求失败是否可区分 | 按原因提供恢复动作 |
| UI-07 | 后台任务 | 开始、暂停、取消、失败和完成的反馈是否一致 | 统一任务状态与控制入口 |
| UI-08 | 窗口与键盘 | 小窗口、大字号、长英文与键盘操作是否可用 | 建立统一交互验收场景 |

UI-07 应包含已记录的首次打开后台任务 / 标签整理窗口场景，已有时序修正与待复测状态以[开发前问题清单](../../1-立项/开发前问题清单.md)为准，不重复宣称发现或修复同一根因。

## 6. 性能问题收集

现有分页追加、徽章增量加载、缓存及流式输出保护需要回归取证，不作为尚未实现的功能重复立项。

| ID | 场景 | 需要测量的问题 | 有证据后评估的方向 |
|---|---|---|---|
| PERF-01 | 启动与窗口首显 | 请求到首次可交互的分段耗时 | 延后非必要初始化，减少首次布局工作 |
| PERF-02 | 大列表切换与滚动 | 长任务、卡顿、持续内存增长 | 控制重算、更新范围与对象生命周期 |
| PERF-03 | 搜索、筛选、排序 | 输入到结果延迟、过期请求资源占用 | 查询取消、缓存身份、执行线程 |
| PERF-04 | 侧栏统计 | 小变更触发的查询量与重绘范围 | 合并刷新、按影响更新 |
| PERF-05 | README、洞察、历史 | 重复请求、解析与视图创建 | 缓存命中、预加载、释放策略 |
| PERF-06 | RAG / AI 长会话 | 长回答、后台生成、切换会话的卡顿 | 验证限频、观察边界与渲染隔离 |
| PERF-07 | 本地模型与索引 | CPU/GPU、内存、数据库竞争 | 准入、调度、批次和释放策略 |
| PERF-08 | 头像与其他缓存 | 长时间运行后的体积和命中率 | 容量上限、淘汰与失效策略 |

测量覆盖小库、万级仓库及更大数据量，记录具体设备与样本规模，并区分冷启动、缓存命中、离线和后台任务运行状态。指标至少包括首屏与搜索延迟分布、主线程卡顿、内存峰值、请求数和缓存命中率。模型提供方耗时与客户端处理耗时分别记录。

复用 [PerformanceTracer](../../../Starcat/Shared/Telemetry/PerformanceTracer.swift)等现有观测能力；没有实测基线前不承诺优化百分比。Linux.do 来源同步还需验证“不开分类也有徽章”不会让列表增加逐行网络请求。

## 7. 实施顺序与版本验收

1. Linux.do 数据通道与识别样本验证，明确可交付范围。
2. Linux.do 从采集到目录、来源标识和详情追溯的完整链路。
3. 设置项映射、信息架构、说明卡片和代表性图标样板。
4. 设置与图标按确认后的样板落地，UI / 性能问题继续按证据分级。
5. App Store / Direct 双渠道回归、升级数据与配置保留、新增功能性能检查。

代码实施前另行确认方案；正式实施时遵循现有任务录入、分支与数据库追加迁移规则。本文不分配迁移版本号，不创建 GitHub / Multica 任务，也不代表发布授权。

本轮只维护规划、设计及必要导航。`docs/功能实现总览.md` 与 Changelog 保持原状；需要登记时再按其独立授权规则处理。
