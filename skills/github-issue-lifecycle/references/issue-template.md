# Issue 草稿模板

仓库存在自己的 Issue 模板时优先使用。否则按以下结构起草。

## Title

使用祈使语气、面向结果的英文标题，并确保它能与相邻工作明确区分。

```text
<Verb> <affected capability> <desired outcome>
```

## Body

```markdown
## Problem

<描述当前行为、故障或限制。相关时保留准确的错误文本。>

## Expected Behavior

<描述修改后的可观察结果。除非实施约束已经确定，否则不要预设实现方式。>

## Scope

- <必要修改>
- <必要修改>

## Acceptance Criteria

- [ ] <可观察、可验证的结果>
- [ ] <相关回归或兼容性要求>
- [ ] <必须完成的测试或人工验收证据>

## Context

<需要时补充复现步骤、环境、截图、日志或链接。没有额外上下文时删除本节。>
```

## 起草规则

- 事实和假设必须分开。
- 保留准确的命令、路径、标识符、版本和错误消息。
- 不写入 secret、token、私有 URL、个人数据或无关日志。
- 除非用户或仓库已经决定，否则不提前写实现细节。
- 不能声称尚未发生的开发、测试或审查已经完成。
