# 审查门禁

使用这些门禁判断实现是否可以提交人工验收。

## 范围门禁

- 最终 diff 能直接对应 Issue 范围。
- 每条 acceptance criterion 都有证据或明确报告的缺口。
- 用户已有的无关修改保持不动。
- 新发现的独立工作以 follow-up Issue 提议，不能静默加入当前范围。

## 验证门禁

- 适用时已经执行仓库要求的 build、test、lint、format 和 static check。
- 可执行行为的变化在合适层级有测试覆盖。
- 依赖环境或人工操作的检查已单独列出。
- 失败和跳过项保持可见，不能汇总成通过。

## 代码审查门禁

- 已审查最终 diff 的正确性和回归风险。
- 安全敏感路径完成明确的安全审查。
- 没有未解决的阻塞或高严重度发现。
- 低严重度发现已经修复、由用户接受，或提议为关联的 follow-up Issue。
- 文档和用户可见消息与实际交付行为一致。

## 人工验收门禁

所有技术门禁通过后，这一门禁仍可能保持未通过。必须由用户或指定 reviewer 明确表示结果已经接受，并且允许评论和关闭 Issue。

以下情况不能视为验收：

- 允许开始实施。
- 单独一次 build 或 test 成功。
- Agent 自己完成代码审查。
- 已创建 commit 或 pull request。
- 用户沉默或没有反对。

附带条件的验收必须先完成条件，再次取得确认后才能关闭。
